## 카테고리 목록 조회 캐싱 적용

### 적용 배경

상품 목록 화면의 카테고리 필터 탭(전체, 상의, 하의 등)을 구성하려면 카테고리 목록을 매번 조회해야 한다.
반면 카테고리는 관리자가 가끔 추가·수정·삭제하는 정적인 데이터다.
조회는 잦고 변경은 드물어 캐싱에 적합하다고 판단해 도입했다.

### v1: Caffeine

서버가 1대뿐이라 여러 서버 간 캐시 공유가 필요 없었다.
Redis는 별도 인프라가 필요한 반면 Caffeine은 라이브러리만 추가하면 되어, 현재 규모에 맞게 Caffeine을 먼저 적용했다.

CategoryService.getCategory()에 @Cacheable을 적용해 카테고리 목록 전체를 하나의 캐시로 저장했다.
생성/수정/삭제 시 @CacheEvict로 이 목록 캐시를 즉시 무효화한다.

캐시 유지 시간은 24시간으로 설정했다.
@CacheEvict가 변경 시점마다 즉시 캐시를 비우기 때문에,
유지 시간 자체는 평소 최신성에 영향을 주지 않고 무효화 로직이 실패했을 때를 대비한 안전장치 역할만 한다.
카테고리는 데이터 양이 적어 길게 유지해도 부담이 없어 24시간으로 잡았다.

**성과**

로컬 10회 반복 측정: 캐시 미스 9.4ms → 캐시 히트 3.7ms (약 2.5배)
EC2 10회 반복 측정: 캐시 미스 25.2ms → 캐시 히트 10.5ms (약 2.4배)

k6 부하테스트(로컬 환경, CPU: AMD Ryzen 9800X3D, RAM: 64GB): 동시 사용자 50 → 150 → 300명으로 단계적 증가, 총 100초 진행.
평균 응답시간 2.01ms → 0.58ms (약 3.5배), p95 3ms → 1ms (약 3배) 개선.

실 트래픽이 없는 학습용 인스턴스에 부하를 주면 예상치 못한 비용이 발생할 수 있어서 EC2에서는 부하테스트를 진행하지 않았다.

**v1의 한계**

- 카테고리 목록 전체를 하나로 캐싱해, 하나만 바뀌어도 전체를 다시 만들어야 한다
- Caffeine은 서버 내부 메모리라 서버가 여러 대면 캐시가 서버마다 별도로 유지된다

### v2: Redis

v1의 한계 중 "서버 여러 대일 때 캐시가 공유되지 않는 문제"를 해결하려고 Redis로 전환했다.
Redis는 애플리케이션과 분리된 저장소라 여러 서버가 하나의 캐시를 공유할 수 있다.

@Cacheable 대신 RedisTemplate을 직접 사용해 캐시 조회/저장/삭제를 코드로 구현했다.

초기에는 카테고리 목록 전체를 하나의 캐시로 저장했으나, 카테고리 하나만
변경되어도 전체를 다시 만들어야 하는 비효율이 있었다. 캐시 키를
카테고리별로 분리(category:{id})해 이 문제를 해결했다. 카테고리 하나만
수정했을 때 해당 캐시만 삭제되고 나머지는 그대로 유지되는 것을 확인했다.
다만 카테고리 개수만큼 캐시 키가 늘어나는 트레이드오프가 있다.

**Redis 장애 대응**

캐시 조회/저장 로직을 try-catch로 감싸, Redis 연결에 실패해도 예외를 던지지 않고 DB 조회로 폴백하도록 처리했다.
타임아웃은 500ms로 설정했다. Redis 정상 시 약 8~20ms, Redis를 강제로 중단시킨 장애 상황에서는 약 1초로 응답하며,
느려지긴 해도 서비스가 완전히 중단되지는 않는 것을 로컬과 EC2 환경 모두에서 확인했다.

**성과**

로컬 10회 반복 측정: 캐시 미스 9.6ms → 캐시 히트 6.2ms (약 1.5배)

EC2 10회 반복 측정: 캐시 미스 27.3ms → 캐시 히트 19.3ms (약 1.4배)

**v1 한계 중 해결된 것**
- 서버 여러 대일 때 캐시 공유 문제
- 카테고리 목록 전체를 통짜로 캐싱하던 문제 (개별 캐싱으로 전환)

캐싱이 부하 상황에서도 효과가 있는지는 v1에서 이미 k6로 확인했다.
v2는 캐시를 저장하는 위치만 서버 내부에서 별도 저장소로 바뀐 것이라,
동일한 목적의 부하테스트를 다시 진행하지는 않았다.

### 결론
현재는 서버가 1대라 v1(Caffeine)만으로도 충분하지만,
서버 확장을 고려해 v2(Redis)를 최종 적용했다.
