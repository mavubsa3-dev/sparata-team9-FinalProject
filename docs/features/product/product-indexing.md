## 상품 목록 조회 인덱싱

### 적용 배경

상품 목록 조회는 사용자가 쇼핑몰에 들어오면 가장 먼저 보게 되는 화면이라
호출 빈도가 높고, 카테고리 필터와 판매중지 상품 제외 조건을 항상 함께 사용한다.
데이터를 늘려놓고 실제로 인덱스 효과를 확인해보기로 했다.

### 구현 과정

테스트를 위해 상품 데이터를 1만 건 생성했다.
EXPLAIN으로 현재 상태를 확인한 결과, category_id 컬럼에는 이미 인덱스가 있었다.
JPA가 연관관계를 만들 때 자동으로 생성해준 것이다.
반면 status 컬럼에는 인덱스가 없어, category_id 조건 없이 status만으로 
조회하면 전체 데이터를 다 훑는 것을 확인했다.

status 컬럼에만 인덱스를 추가로 만들어봤지만 효과가 없었다.
확인해보니 HIDDEN 상품은 약 5%뿐이고 나머지 95%(판매중/품절)는 status <> 'HIDDEN' 조건에 걸렸다.
status는 값의 종류가 3개뿐이고 그중 대부분이 한 값(ON_SALE)에 몰려 있어 카디널리티가 낮은 컬럼이었다.
인덱스는 카디널리티가 높을수록, 즉 값의 종류가 다양해 조건을 걸었을 때 데이터가 확 줄어들수록 효과적인데,
status는 그 반대 특성을 가진 컬럼이라 인덱스를 걸어도 효과가 없었던 것이다.

실제 조회는 category_id와 status를 함께 사용하므로, 두 컬럼을 묶은 복합 인덱스로 다시 만들었다.
category_id는 조건을 걸면 조회 대상이 크게 줄어드는 반면, status는 조건을 걸어도 거의 줄어들지 않는다.
더 많이 줄여주는 category_id를 인덱스 앞쪽에 두었다.

### 성과

인덱스 적용 후, category_id 조건이 있을 때 조회 대상이 9,865건에서 1,429건으로 줄었다.
실제 응답 속도는 인덱스 적용 전후로 약 20ms 내외로 큰 차이가 없었다.
카테고리 7개에 상품 1만 건이 나뉘어 있어 카테고리당 데이터 양이 아직 1,400건 수준이라,
인덱스 없이도 충분히 빠르게 처리할 수 있는 규모이기 때문으로 분석된다.

### 한계 및 판단

지금 다룬 필터 조건은 category_id와 status 두 가지뿐이다.
category_id는 사용자가 직접 선택하는 값이지만, status는 사용자가
선택하는 게 아니라 판매중지 상품을 숨기기 위해 항상 붙는 조건이라,
실제 사용자 시나리오에서 이 두 조건의 조합이 얼마나 의미 있는지는
가격 필터, 정렬, 키워드 검색 같은 조건이 추가된 이후에 다시 검증해볼 필요가 있다.

다만 지금 있는 조건 기준으로는, 향후 데이터가 늘어날 경우를 대비해 인덱스를 코드에 반영했다.
인덱스는 쓰기 시 갱신 비용이 있지만,
상품 수정/삭제보다 조회가 훨씬 빈번할 것으로 예상되어 이 비용은 크지 않다고 판단했다.
다만 실제 쓰기 빈도를 정량적으로 측정하지는 않았다.

### 인덱스를 코드로 관리한 이유

인덱스는 JPA 엔티티의 @Table indexes 설정으로 코드에 명시했다. 콘솔에서
직접 SQL로 인덱스를 만드는 방식은 그 DB 하나에만 적용되어 다른 환경에는
반영되지 않는 반면, 코드에 명시하면 DB를 새로 만들 때마다 자동으로
함께 생성되어 팀원 모두에게 동일하게 적용된다.
