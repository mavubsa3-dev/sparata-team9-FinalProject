## 상품 목록 조회 인덱싱

### 적용 배경

상품 목록 조회 API는 카테고리 필터와 판매중지 상품 제외 조건을 항상 함께 사용한다.
상품 데이터가 많아질수록 이 조건들로 조회하는 속도가 느려질 수 있어,
데이터를 늘려놓고 인덱스 효과를 확인해보기로 했다.

### 구현 과정

테스트를 위해 상품 데이터를 1만 건 생성했다.
인덱스 적용 전 EXPLAIN으로 확인한 결과, category_id 컬럼에는 이미 인덱스가 있었다.
JPA가 연관관계를 만들 때 자동으로 생성해준 것이다.
반면 status 컬럼에는 인덱스가 없어, category_id 조건 없이 status만으로
조회하면 전체 데이터를 다 훑는 것을 확인했다.

status 컬럼에만 인덱스를 추가로 만들어봤지만 효과가 없었다.
확인해보니 status <> 'HIDDEN' 조건은 전체 데이터의 약 95%에 해당했다.
찾아야 할 데이터가 이렇게 많으면, 인덱스를 이용해서 하나씩 찾는 것보다
그냥 테이블 전체를 처음부터 끝까지 훑어보는 게 더 빠르다.
그래서 인덱스를 만들어도 실제로는 사용되지 않았다.

실제 조회는 category_id와 status를 함께 사용하므로, 두 컬럼을 묶은 복합 인덱스로 다시 만들었다.
category_id는 조건을 걸면 조회 대상이 크게 줄어드는 반면, status는 조건을 걸어도 거의 줄어들지 않는다.
더 많이 줄여주는 category_id를 인덱스 앞쪽에 두었다.

### 성과

인덱스 적용 후, category_id 조건이 있을 때 조회 대상이 9,865건에서 1,429건으로 줄었다.
실제 응답 속도는 인덱스 적용 전후로 약 20ms 내외로 큰 차이가 없었다.
카테고리당 데이터 양이 아직 1,400건 수준이라, 인덱스 없이도 충분히 빠르게 처리할 수 있는 규모이기 때문으로 분석된다.

### 한계 및 판단

현재 규모에서는 체감 성능 개선이 거의 없었지만, 향후 데이터가 늘어날
경우를 대비해 인덱스를 코드에 반영했다. 인덱스는 쓰기 시 갱신 비용이
있지만, 상품은 조회에 비해 변경이 드물어 이 비용은 크지 않다고 판단했다.

인덱스는 JPA 엔티티의 @Table indexes 설정으로 코드에 명시했다.
콘솔에서 직접 SQL로 인덱스를 만드는 방식은 그 DB 하나에만 적용되어
다른 환경에는 반영되지 않는 반면, 코드에 명시하면 DB를 새로 만들 때마다
자동으로 함께 생성되어 팀원 모두에게 동일하게 적용된다.
